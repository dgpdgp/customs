# ТЗ: программа «PDF счёта-проформы и упаковочного листа → Excel»

Документ описывает, что было сделано вручную на пилотном файле и как повторить то же самое программой.
По этому описанию разработчик должен суметь написать программу, которая на пилотном файле даст тот же результат.
Эталон для проверки — `docs/golden/UZ95-039-045-2026_expected.json` (раздел 9).

---

## 1. Что делает программа

**Вход:** PDF с отсканированными счетами-проформами (FACTURA PROFORMA / PROFORMA INVOICE) и упаковочными листами (PACKING LIST) отправителя.

**Выход:**
1. Excel-файл: таблица товаров (артикул, наименование на русском, код ТН ВЭД, количество, единица измерения, стоимость, вес брутто, вес нетто), а также листы с исходными данными, сверкой и замечаниями (раздел 6).
2. Необязательно: PDF «Рабочая спецификация» с теми же данными и перечнем того, что отправитель должен исправить (раздел 7).

**Главное требование — точность.** Каждое значение переносится ровно так, как напечатано. Каждое число проверяется арифметически и сверяется между счётом и упаковочным листом. Всё, что не сходится, попадает в отчёт. Программа ничего не «исправляет» молча.

---

## 2. Как это было сделано в пилоте (важно для понимания)

Пилот: файл `8c38d916-supporting_4.pdf`, 14 страниц (7 пар «счёт + упаковочный лист»), счета UZ95-039-2026 … UZ95-045-2026 от 21.09.2026.

| Шаг | Как сделано в пилоте | Что нужно в программе |
|---|---|---|
| Проверка текстового слоя | `pdftotext` — текста нет, файл состоит из картинок | Так же |
| Рендер страниц | `pdftoppm -r 300 -png` → 3508×2480 px на страницу | Так же |
| Чтение таблиц | ИИ-ассистент **читал увеличенные фрагменты изображений глазами** (обрезка Pillow), значения вводились в структуру данных вручную | Автоматическое распознавание: модель с компьютерным зрением (Claude API) или OCR — раздел 5.5 |
| Проверка чтения | Независимая повторная перечитка всех 14 страниц отдельными проверяющими; спорные места — вторым проверяющим | Два независимых прохода распознавания + сравнение — раздел 5.6 |
| Арифметика и сверки | Python (`decimal.Decimal`) | Так же — раздел 5.8 |

**Результат пилота:** 40 строк, 129 шт, 36 280,25 EUR по строкам, нетто 16 194,95 кг, брутто 17 665,00 кг.
Повторная независимая перечитка нашла **одну** ошибку первого прохода: в наименовании Z594470 на скане «КЛЕ**Ш**Е», а не «КЛЕ**Щ**Е». Поэтому второй проход обязателен.

## 3. Входные документы: структура

Страницы идут парами: нечётная — счёт, следующая чётная — упаковочный лист к нему. Программа не должна на это полагаться: тип страницы определяется по заголовку, пара — по номеру документа (раздел 5.3).

### 3.1. Счёт-проформа (FACTURA PROFORMA / PROFORMA INVOICE)

**Шапка:** номер вида `UZ95-039-2026` (справа вверху), дата `Fecha / Date / Дата` (21.09.2026), получатель (Destinatario / Consignee), адрес доставки, отправитель (Remitente / Shipper), контактное лицо, «ПРОИСХОЖДЕНИЕ ГРУЗА / ORIGIN OF THE GOODS: EU».

**Таблица товаров** (заголовки двуязычные, слева направо):

| Колонка в документе | Поле | Пример | Примечание |
|---|---|---|---|
| Bulto nr / № Паллета | `bulto` | `10` | Номер паллеты в отправке, **не совпадает** с номером места в упаковочном листе |
| Artículo o nº serie / Реф. | `article` | `Z5069905A` | Латиница + цифры |
| Cant. / К-во | `qty` | `1` | Целое |
| U.M. / Ед.из | `um` | `UN` | В Excel выводится как «шт» |
| Embalaje / Упаковка | `packaging` | `PM` | Коды расшифрованы внизу счёта: CC — картонная коробка, PM — деревянная палета, CM — деревянный ящик, BP — пластиковый пакет |
| Descripcion | `description_es` | `EJE DE TRACCION COMPLETO REPARADO` | Испанский |
| Наименование | `name_ru` | `КОМПЛЕКТ ВАЛОВ С НАБОРОМ КОЛЕС И ТЯГОВЫМ ДВИГАТЕЛЕМ` | Может занимать 2 строки в ячейке |
| Partida arancelaria / Код ТН ВЭД | `hs_code` | `8607191009` | 10 цифр, хранить **как текст** |
| Цена, euro | `unit_price` | `€ 1 680,00` | |
| Precio coste eur / Итого стоимость EUR | `value` | `1 680,00 €` | |

**Итоговая строка:** «TOTAL FACTURA» (сумма, EUR) и итог в колонке «К-во». Ниже: `IVA 00,0% s/`, примечания (INCOTERMS 2020 DAP Madrid, происхождение Spain, контракт EXP-72, «Goods value is for customs purposes only», «… included total 0,50 KG of recycled plastic package …»).

### 3.2. Упаковочный лист (PACKING LIST, `Ref: PL UZ95-039-2026`)

| Колонка в документе | Поле | Пример | Примечание |
|---|---|---|---|
| SEAT / МЕСТО | `seat` | `1` | Встречается место **«0»** (PL 042) |
| DIMENSIONS / ДхШхВ (см) | `dims_cm` | `200x260x150` | Объединённая ячейка, если в месте несколько позиций |
| Ficha / Артикул | `article` | `Z5069905A` | Должен совпадать со счётом |
| Material | `description_es` | | Испанский |
| Материал | `name_ru` | | Должен совпадать со счётом |
| Q-ty, pc / Кол-во, шт | `qty` | `1` | |
| Peso artículo / Вес за шт. (Kg) | `unit_net_kg` | `4500,000` | 3 знака после запятой |
| Total Weigth, Net, kg / Нетто | `net_kg` | `4 500,00` | |
| Total Weigth, Gross, kg / Брутто | `seat_gross_kg` | `4800,00` | **На место целиком.** Если в месте несколько позиций — одна объединённая ячейка на все строки места |

**Итоговая строка:** TOTAL — итог количества, нетто и брутто.

### 3.3. Формат чисел

- Десятичный разделитель — **запятая**, разделитель тысяч — **пробел** (в т. ч. неразрывный), иногда без разделителя: `4500,000`, `2305,00`.
- Знак евро слева или справа: `€ 1 680,00`, `1 680,00 €`.
- Все расчёты — в `decimal.Decimal`, **не во float**.

### 3.4. Ловушки, найденные в пилоте

1. **Печать поверх текста** (синяя круглая печать) перекрывает наименования, количества и итоги в упаковочных листах. Текст под ней читаем, но распознавание ошибается чаще.
2. **Брутто только на место.** В PL 041–045 брутто — одна объединённая ячейка на несколько позиций. Его нужно распределять (раздел 5.9) и помечать как расчётное.
3. **Нумерация мест.** Номер паллеты в счёте (Bulto nr: 10, 11, 5, 6, 7, 2, 2, 1, 3, 4) и номер места в PL (1, 2, 3, 0) — разные нумерации. В счетах 041 и 042 указан один и тот же номер паллеты 2, а в PL это разные места (место 1 размером 120×80×65 см и брутто 75 кг; место «0» размером 60×40×40 см и брутто 10 кг).
4. **Повтор артикула.** Один артикул может стоять в нескольких строках (Z5069905A — 2 строки, Z5069970A — 3 строки на разных паллетах). Строки **не объединять**.
5. **Опечатки источника сохранять:** «ЭЛЕКТРОНУМАТИЧЕСКИЙ МОДУЛЯТОР (ЭПМ)», «КЛЕШЕ (ПАТРОН) КАЛИБРОВОЧНЫЙ». В данные — как напечатано, в замечания — что не так.
6. **Похожие буквы:** Ш/Щ, О/0, З/3, латинская/кириллическая «A», «C», «V». В пилоте «КЛЕШЕ» при первом чтении было ошибочно прочитано как «КЛЕЩЕ».
7. **Двойные пробелы** в источнике («ПЛАТА ТЕМПЕРАТУРЫ  (PT100)»). Пробелы нормализуются до одного; содержательной ошибкой это не считается.
8. **Низкое разрешение даёт ложные опечатки.** На превью шириной около 1170 px «Patentes» читалось как «Pateates», «AllBest» — как «Al Best». На 300 dpi текст правильный. Читать только с 300 dpi и выше.
9. **Ошибка итога в самом документе.** В счёте 043 TOTAL FACTURA = 13 567,15, а сумма строк = 13 715,71. Итог не включает последнюю строку (148,56). Программа должна это ловить (раздел 5.8), а не подгонять.

## 4. Модель данных

Одна строка товара (после нормализации):

```text
invoice            str      "UZ95-043-2026"
bulto              int      1                (из счёта)
seat               int      1                (из PL)
dims_cm            str      "120x80x110"     (из PL)
article            str      "Z10014704"
description_es     str      "MODULADOR ELECTRONEUMATICO (EPM) REP"
name_ru            str      "ЭЛЕКТРОНУМАТИЧЕСКИЙ МОДУЛЯТОР (ЭПМ)"   (как напечатано)
hs_code            str      "8607998000"     (текст, ровно 10 цифр)
qty                int      1
um                 str      "UN"
packaging          str      "PM"
unit_price_eur     Decimal  735.92
value_eur          Decimal  735.92
```

Плюс по каждому документу — напечатанные итоги: кол-во и TOTAL FACTURA из счёта; кол-во, нетто и брутто из PL.

## 5. Конвейер обработки

### 5.1. Проверка текстового слоя

`pdftotext -layout file.pdf -` — если текст есть, таблицы извлекать из текста (например, `pdfplumber`), без распознавания картинок. В пилоте текста не было.

### 5.2. Рендер

`pdftoppm -r 300 -png file.pdf p` → `p-01.png … p-14.png`, 3508×2480 px (A4 альбом).

### 5.3. Тип страницы и пары документов

- Счёт: в заголовке «FACTURA PROFORMA / PROFORMA INVOICE», номер `UZ95-NNN-YYYY`.
- Упаковочный лист: «PACKING LIST», `Ref: PL UZ95-NNN-YYYY`.
- Пара — по одинаковому номеру. Счёт без PL (или наоборот) — ошибка в отчёте.

Номер и тип можно распознать тем же вызовом модели по фрагменту шапки (раздел 5.5).

### 5.4. Нарезка на фрагменты

Целую страницу распознавать нельзя: мелкий текст при уменьшении искажается (см. п. 8 раздела 3.4). В пилоте использовались такие области (координаты в px при 300 dpi):

| Что | Область |
|---|---|
| Таблица счёта | y ≈ 690…1600 (зависит от числа строк) |
| Таблица PL | y ≈ 940…1600 |
| Левая половина | x 0…1800 |
| Правая половина | x 1700…3508 (перекрытие 100 px, чтобы не резать текст) |
| Высокие таблицы | Полосы высотой ~350 px с перекрытием |
| Шапка (номер, отправитель) | Отдельный фрагмент верхней части страницы |

Координаты пилота жёсткие. В программе лучше находить границы таблицы автоматически (по линиям сетки), а координаты пилота использовать как запасной вариант. Каждый фрагмент должен содержать строку заголовков колонок или передаваться вместе с ней, чтобы было понятно, какая это колонка.

### 5.5. Распознавание

**Рекомендуемый способ — модель Claude с компьютерным зрением и строгой JSON-схемой ответа.**
OCR (например, tesseract) хуже справляется с таблицами, печатью поверх текста и смешением кириллицы и латиницы. Если используется OCR, все проверки раздела 5.8 и второй проход раздела 5.6 становятся ещё важнее.

Правила запроса к модели (вписать в промпт):

1. Переписывать каждое значение **посимвольно как напечатано**, ничего не исправлять. Опечатки сохранять.
2. Числа возвращать **строкой как напечатано** (`"1 680,00 €"`), а разбирать их в коде (раздел 5.7). Так легче искать ошибки.
3. Если символ или значение не читается (например, под печатью) — **не угадывать**, а перечислить поле в `unreadable`.
4. Возвращать все строки таблицы и итоговую строку отдельно.
5. Коды ТН ВЭД — строкой.

Пример вызова на Python (Anthropic SDK). Параметры сверены с SDK `anthropic` 1.12.1; **реальный вызов API на пилоте не выполнялся** — проверить на эталоне (раздел 9).

```python
import base64, json

    "type": "object",

        data = base64.standard_b64encode(f.read()).decode("utf-8")
    return {"type": "image", "source": {"type": "base64", "media_type": "image/png", "data": data}}

def extract_invoice(fragment_paths, instructions):
    response = client.beta.messages.create(
        model="claude-opus-5-5",
        max_tokens=16000,
        betas=["server-side-fallback-2026-07-01"],
        fallbacks="default",
        output_config={"effort": "high",
                       "format": {"type": "json_schema", "schema": INVOICE_SCHEMA}},
```

Схема для упаковочного листа строится так же. Поля строки: `seat`, `dims_cm`, `article`, `description_es`, `name_ru`, `qty`, `unit_net`, `net`, `seat_gross`, `unreadable`. Итоговые поля: `total_qty`, `total_net`, `total_gross`. Для объединённой ячейки брутто модель должна вернуть значение на каждой строке места либо явно указать, к каким строкам оно относится. Это нужно оговорить в промпте.

### 5.6. Второй независимый проход (обязательно)

1. Распознать каждый документ **дважды** независимо: другая нарезка фрагментов и/или другая формулировка промпта.
2. Сравнить два результата **поле за полем**.
3. По каждому расхождению сделать третий запрос: дать сильно увеличенный фрагмент одной ячейки и спросить, что именно там напечатано (в пилоте именно так проверено Ш/Щ).
4. Если и после этого есть сомнение или поле есть в `unreadable` — пометить поле «требует проверки человеком» и показать в отчёте. Не угадывать.

### 5.7. Нормализация

Разбор чисел (проверено на всех значениях пилота):

```python
import re
from decimal import Decimal

def parse_number(raw: str) -> Decimal:
    """'€ 1 680,00' / '1 680,00 €' / '4500,000' / '13 567,15 €' -> Decimal"""
    s = raw.replace("€", "").replace("EUR", "")
    s = re.sub(r"[\s  ]", "", s)   # пробелы, NBSP, узкий NBSP
    s = s.replace(",", ".")
    if not re.fullmatch(r"-?\d+(\.\d+)?", s):
        raise ValueError(f"Не число: {raw!r}")
    return Decimal(s)
```

Прочие правила:

- `hs_code`: только цифры, ровно 10, хранить текстом.
- `qty`: целое.
- Наименования: обрезать пробелы по краям, повторные пробелы заменять одним. **Больше ничего не менять.**
- `UN` → «шт» только при выводе в основную таблицу; в исходных данных оставить `UN`.

### 5.8. Проверки

Каждая проверка даёт результат «OK» или «ошибка», и результат виден в отчёте.

**По каждой строке:**

| № | Проверка | Допуск |
|---|---|---|
| С1 | `qty × unit_price = value` | 0,005 EUR |
| С2 | `qty(PL) × unit_net = net` | 0,0005 кг |
| С3 | Артикул в счёте = артикул в PL | Точно |
| С4 | Наименование (рус.) в счёте = в PL | Точно, после нормализации пробелов |
| С5 | Количество в счёте = в PL | Точно |
| С6 | Код ТН ВЭД — ровно 10 цифр | |
| С7 | Стоимость, нетто, брутто > 0 | |

**По каждому документу:**

| № | Проверка |
|---|---|
| Д1 | Сумма `value` по строкам = TOTAL FACTURA |
| Д2 | Сумма количества = итог «К-во» счёта = итог PL |
| Д3 | Сумма нетто по строкам = итог нетто PL |
| Д4 | Сумма брутто по местам = итог брутто PL |
| Д5 | Брутто > нетто (по каждому месту и в целом) |
| Д6 | Строки счёта и PL сопоставлены один к одному (по порядку и артикулу), лишних и потерянных нет |

**По всему файлу (подсказки, не ошибки):**

| № | Что ищем | Пример из пилота |
|---|---|---|
| Ф1 | Одинаковое наименование — разные коды ТН ВЭД | «ПОПЕРЕЧНЫЙ АНТИВИБРАЦИОННЫЙ АМОРТИЗАТОР»: Z5050055A → 8607919000, остальные → 8607199000 |
| Ф2 | Один номер паллеты в разных счетах | Паллета 2 в 041 и 042 |

Если их автоматизировать — только как отдельный список «требует проверки» с объяснением. Правильный код определяет декларант.

### 5.9. Распределение веса брутто

Если в месте одна позиция, её брутто = брутто места.

Если позиций несколько:

1. Доля позиции = брутто места × нетто позиции / нетто места, округлённая до 0,01 кг (математическое округление, ROUND_HALF_UP).
2. Остаток округления (брутто места − сумма долей) относится на позицию с **наибольшим нетто** в месте; при равенстве — на первую из них.
3. Сумма по месту обязана **точно** совпасть с брутто места из PL.
4. Такие значения помечаются как расчётные (в пилоте — жёлтая заливка).

```python
from decimal import Decimal, ROUND_HALF_UP

def allocate_gross(nets: list[Decimal], seat_gross: Decimal) -> list[Decimal]:
    total = sum(nets)
    shares = [(seat_gross * n / total).quantize(Decimal("0.01"), ROUND_HALF_UP) for n in nets]
    i_max = max(range(len(nets)), key=lambda i: (nets[i], -i))   # первая из наибольших
    shares[i_max] = seat_gross - (sum(shares) - shares[i_max])
    return shares

# Пилот, PL 041: нетто [12.60, 2.00, 0.20, 0.25, 1.20, 27.00], брутто места 75.00
#   -> [21.85, 3.47, 0.35, 0.43, 2.08, 46.82]
# Пилот, PL 042: нетто [0.50, 5.00, 2.00], брутто 10.00 -> [0.67, 6.66, 2.67]
```

В Excel то же самое сделано формулами (раздел 6.2, столбцы W–Z), чтобы расчёт был виден и пересчитывался.
