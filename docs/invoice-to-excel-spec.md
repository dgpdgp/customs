# ТЗ: программа «PDF счёта-проформы и упаковочного листа → Excel»

Документ описывает, что было сделано вручную на пилотном файле и как повторить то же самое программой.
По этому описанию разработчик должен суметь написать программу, которая на пилотном файле даст тот же результат.
Эталон для проверки — `docs/golden/UZ95-039-045-2026_expected.json` (раздел 9).

---

## 1. Что делает программа

**Вход:** PDF с отсканированными счетами-проформами (FACTURA PROFORMA / PROFORMA INVOICE) и упаковочными листами (PACKING LIST) отправителя.

**Выход:**
1. Excel-файл: таблица товаров (артикул, наименование на русском, код ТН ВЭД, количество, единица измерения, стоимость, вес брутто, вес нетто), а также листы с исходными данными, сверкой и замечаниями (раздел 6).
2. Необязательно: PDF «Рабочая спецификация» с теми же данными и перечнем того, что отправитель должен исправить (раздел 7).

**Главное требование — точность.** Каждое значение переносится ровно так, как напечатано. Каждое число проверяется арифметически и сверяется между счётом и упаковочным листом. Всё, что не сходится, попадает в отчёт. Программа ничего не «исправляет» молча.

---

## 2. Как это было сделано в пилоте (важно для понимания)

Пилот: файл `8c38d916-supporting_4.pdf`, 14 страниц (7 пар «счёт + упаковочный лист»), счета UZ95-039-2026 … UZ95-045-2026 от 21.09.2026.

| Шаг | Как сделано в пилоте | Что нужно в программе |
|---|---|---|
| Проверка текстового слоя | `pdftotext` — текста нет, файл состоит из картинок | Так же |
| Рендер страниц | `pdftoppm -r 300 -png` → 3508×2480 px на страницу. Сам скан — 200 ppi (JPEG 1653×2338 на страницу A4 книжной ориентации с поворотом 90°); 300 dpi — рендер для удобного нарезания, деталей он не добавляет | Так же, раздел 5.2 |
| Чтение таблиц | ИИ-ассистент **читал увеличенные фрагменты изображений глазами** (обрезка Pillow), значения вводились в структуру данных вручную | Автоматическое распознавание: модель с компьютерным зрением (Claude API) или OCR — раздел 5.5 |
| Проверка чтения | Независимая повторная перечитка всех 14 страниц отдельными проверяющими; спорные места — вторым проверяющим | Два независимых прохода распознавания + сравнение — раздел 5.6 |
| Арифметика и сверки | Python (`decimal.Decimal`) | Так же — раздел 5.8 |
| Распределение брутто | Python + формулы Excel | Так же — раздел 5.9 |
| Excel | `openpyxl`, формулы, пересчёт через LibreOffice | Так же — раздел 6 |
| PDF-отчёт | `reportlab` + шрифт DejaVu Sans (кириллица) | Так же — раздел 7 |

**Вывод и честные оговорки:**

1. Готовой OCR-программы в пилоте не было, распознавание выполнял ИИ-ассистент. Проверки, распределение брутто, Excel и PDF — обычный детерминированный код; его нужно повторить.
2. **Разделы 5.4–5.6 (автоматическая нарезка, распознавание моделью, второй проход) — проект, а не описание готового.** В пилоте нарезку делал ассистент вручную для чтения глазами; автоматическая сборка строк из фрагментов и вызов API в пилоте не реализовывались и не запускались. Их работоспособность надо подтвердить приёмочным тестом (раздел 9).
3. **Замечания по классификации** (лист «Замечания», столбец K, раздел 3 PDF) написал ИИ-ассистент по общим сведениям о структуре ГС, без сверки с текстом действующего ТН ВЭД. Отдельного эксперта в пилоте не было. Программа может воспроизвести только автоматические замечания из 6.4; классификацию она не определяет.
4. **В пилотном Excel значения PL для артикула, наименования и количества введены один раз и равны значениям счёта**, поэтому проверки С3–С5 там «OK» по построению. Реальная сверка счёта с PL делалась глазами и независимой перечиткой сканов. В программе эти поля из PL должны извлекаться независимо от счёта.

**Результат пилота:** 40 строк, 129 шт, 36 280,25 EUR по строкам, нетто 16 194,95 кг, брутто 17 665,00 кг.
Повторная независимая перечитка нашла **одну** ошибку первого прохода: в наименовании Z594470 на скане «КЛЕ**Ш**Е», а не «КЛЕ**Щ**Е». Поэтому второй проход обязателен.

## 3. Входные документы: структура

Страницы идут парами: нечётная — счёт, следующая чётная — упаковочный лист к нему. Программа не должна на это полагаться: тип страницы определяется по заголовку, пара — по номеру документа (раздел 5.3).

### 3.1. Счёт-проформа (FACTURA PROFORMA / PROFORMA INVOICE)

**Шапка:** номер вида `UZ95-039-2026` (справа вверху), дата `Fecha / Date / Дата` (21.09.2026), получатель (Destinatario / Consignee), адрес доставки, отправитель (Remitente / Shipper), контактное лицо, «ПРОИСХОЖДЕНИЕ ГРУЗА / ORIGIN OF THE GOODS: EU».

**Таблица товаров** (заголовки двуязычные, слева направо):

| Колонка в документе | Поле | Пример | Примечание |
|---|---|---|---|
| Bulto nr / № Паллета | `bulto` | `10` | Номер паллеты в отправке, **не совпадает** с номером места в упаковочном листе |
| Artículo o nº serie / Реф. | `article` | `Z5069905A` | Латиница + цифры |
| Cant. / К-во | `qty` | `1` | Целое |
| U.M. / Ед.из | `um` | `UN` | В Excel выводится как «шт» |
| Embalaje / Упаковка | `packaging` | `PM` | Коды расшифрованы внизу счёта: CC — картонная коробка, PM — деревянная палета, CM — деревянный ящик, BP — пластиковый пакет |
| Descripcion | `description_es` | `EJE DE TRACCION COMPLETO REPARADO` | Испанский |
| Наименование | `name_ru` | `КОМПЛЕКТ ВАЛОВ С НАБОРОМ КОЛЕС И ТЯГОВЫМ ДВИГАТЕЛЕМ` | Может занимать 2 строки в ячейке |
| Partida arancelaria / Код ТН ВЭД | `hs_code` | `8607191009` | 10 цифр, хранить **как текст** |
| Цена, euro | `unit_price` | `€ 1 680,00` | |
| Precio coste eur / Итого стоимость EUR | `value` | `1 680,00 €` | |

**Итоговая строка:** «TOTAL FACTURA» (сумма, EUR) и итог в колонке «К-во». Ниже: `IVA 00,0% s/`, примечания (INCOTERMS 2020 DAP Madrid, происхождение Spain, контракт EXP-72, «Goods value is for customs purposes only», «… included total 0,50 KG of recycled plastic package …»).

### 3.2. Упаковочный лист (PACKING LIST, `Ref: PL UZ95-039-2026`)

| Колонка в документе | Поле | Пример | Примечание |
|---|---|---|---|
| SEAT / МЕСТО | `seat` | `1` | Встречается место **«0»** (PL 042). Если в месте несколько позиций, ячейка **объединена** на все строки места: номер нужно распространить на каждую строку |
| DIMENSIONS / ДхШхВ (см) | `dims_cm` | `200x260x150` | Объединённая ячейка, если в месте несколько позиций |
| Ficha / Артикул | `article` | `Z5069905A` | Должен совпадать со счётом |
| Material | `description_es` | | Испанский |
| Материал | `name_ru` | | Должен совпадать со счётом |
| Q-ty, pc / Кол-во, шт | `qty` | `1` | |
| Peso artículo / Вес за шт. (Kg) | `unit_net_kg` | `4500,000` | 3 знака после запятой |
| Total Weigth, Net, kg / Общий вес, Нетто, кг | `net_kg` | `4 500,00` | «Weigth» — как напечатано в документе |
| Total Weigth, Gross, kg / Общий вес, брутто, кг | `seat_gross_kg` | `4800,00` | **На место целиком.** Если в месте несколько позиций — одна объединённая ячейка на все строки места |

**Итоговая строка:** TOTAL — итог количества, нетто и брутто.

### 3.3. Формат чисел

- Десятичный разделитель — **запятая**, разделитель тысяч — **пробел** (в т. ч. неразрывный), иногда без разделителя: `4500,000`, `2305,00`.
- Знак евро слева или справа: `€ 1 680,00`, `1 680,00 €`.
- Все расчёты — в `decimal.Decimal`, **не во float**.

### 3.4. Ловушки, найденные в пилоте

1. **Печать поверх текста** (синяя круглая печать) перекрывает наименования, количества и итоги в упаковочных листах. Текст под ней читаем, но распознавание ошибается чаще.
2. **Брутто только на место.** В PL 041–045 брутто — одна объединённая ячейка на несколько позиций. Его нужно распределять (раздел 5.9) и помечать как расчётное.
3. **Нумерация мест.** Номер паллеты в счёте (Bulto nr: 10, 11, 5, 6, 7, 2, 2, 1, 3, 4) и номер места в PL (1, 2, 3, 0) — разные нумерации. В счетах 041 и 042 указан один и тот же номер паллеты 2, а в PL это разные места (место 1 размером 120×80×65 см и брутто 75 кг; место «0» размером 60×40×40 см и брутто 10 кг).
4. **Повтор артикула.** Один артикул может стоять в нескольких строках (Z5069905A — 2 строки, Z5069970A — 3 строки на разных паллетах). Строки **не объединять**.
5. **Опечатки источника сохранять:** «ЭЛЕКТРОНУМАТИЧЕСКИЙ МОДУЛЯТОР (ЭПМ)», «КЛЕШЕ (ПАТРОН) КАЛИБРОВОЧНЫЙ». В данные — как напечатано, в замечания — что не так.
6. **Похожие буквы:** Ш/Щ, О/0, З/3, латинская/кириллическая «A», «C», «V». В пилоте «КЛЕШЕ» при первом чтении было ошибочно прочитано как «КЛЕЩЕ».
7. **Двойные пробелы** в источнике («ПЛАТА ТЕМПЕРАТУРЫ  (PT100)»). Пробелы нормализуются до одного; содержательной ошибкой это не считается.
8. **Низкое разрешение даёт ложные опечатки.** На превью шириной около 1170 px «Patentes» читалось как «Pateates», «AllBest» — как «Al Best». На 300 dpi текст правильный. Читать только с 300 dpi и выше.
9. **Ошибка итога в самом документе.** В счёте 043 TOTAL FACTURA = 13 567,15, а сумма строк = 13 715,71. Итог не включает последнюю строку (148,56). Программа должна это ловить (раздел 5.8), а не подгонять.

10. **Страницы — книжные A4 с поворотом 90°**, внутри JPEG 1653×2338 при 200 ppi. `pdftoppm` поворот учитывает (получается альбомная картинка 3508×2480 при 300 dpi). Если картинки извлекаются иначе (`pdfimages`, библиотека без учёта `/Rotate`), их нужно повернуть, иначе все координаты раздела 5.4 неверны.
11. **`pdftotext` для скана возвращает не пустую строку:** 14 байт, все — символы перевода страницы. Проверка «вывод не пуст» даст ложное «текстовый слой есть» (раздел 5.1).
12. **Латиница и кириллица неразличимы** в буквах A, B, C, E, H, K, M, O, P, T, X, Y (раздел 5.7).

## 5. Конвейер обработки

### 5.1. Проверка текстового слоя

`pdftotext -layout file.pdf - | tr -d '[:space:]' | wc -c` — число непробельных символов. Если на страницах их заметно больше нуля (например, больше 100 на страницу), таблицы извлекать из текста (например, `pdfplumber`), без распознавания картинок. В пилоте: 0 непробельных символов на весь файл (14 байт — одни переводы страниц), текстового слоя нет.

### 5.2. Рендер

`pdftoppm -r 300 -png file.pdf p` → `p-01.png … p-14.png`, 3508×2480 px (A4 альбом). Исходные страницы — A4 книжные с `/Rotate 90`, скан 200 ppi; `pdftoppm` поворачивает страницу сам. Если картинки берутся другим способом, повернуть их по `/Rotate` (`pdfinfo` показывает строку `Page N rot:`). Не рендерить ниже 300 dpi: на превью шириной ~1170 px появляются ложные опечатки (раздел 3.4, п. 8).

### 5.3. Тип страницы и пары документов

- Счёт: в заголовке «FACTURA PROFORMA / PROFORMA INVOICE», номер `UZ95-NNN-YYYY`.
- Упаковочный лист: «PACKING LIST», `Ref: PL UZ95-NNN-YYYY`.
- Пара — по одинаковому номеру. Счёт без PL (или наоборот) — ошибка в отчёте.

Номер и тип можно распознать тем же вызовом модели по фрагменту шапки (раздел 5.5).

### 5.4. Нарезка на фрагменты

> **Статус: проект.** В пилоте фрагменты вырезал ассистент вручную (Pillow), чтобы читать глазами. Автоматическая нарезка и сборка строк, описанные ниже, в пилоте не реализовывались; проверить их нужно на эталоне (раздел 9).

Целую страницу распознавать нельзя: мелкий текст при уменьшении искажается (раздел 3.4, п. 8). Координаты ниже — из пилота (px, рендер 300 dpi, 3508×2480). **У счёта и упаковочного листа они разные**, использовать координаты счёта для PL нельзя:

| Что | Счёт | Упаковочный лист |
|---|---|---|
| Верх таблицы по y | ≈ 690 | ≈ 940 |
| Низ таблицы по y | зависит от числа строк (в пилоте 940…1600) | зависит от числа строк (в пилоте 1170…1600) |
| Левая половина по x | 0…1800 | 180…1800 |
| Правая половина по x | 1700…3508 | 1450…3300 |
| Средняя полоса для высоких таблиц (необязательно) | — | 550…2250 |
| Высокие таблицы по y | полосы ~350 px с перекрытием | то же |
| Шапка (реквизиты, номер, дата) | отдельный фрагмент верха страницы | то же |

Координаты жёсткие. В программе границы таблицы и колонок лучше находить автоматически (по линиям сетки), а координаты пилота использовать как запасные.

**Сборка строк из фрагментов (проект):**

1. Строки **нельзя** склеивать и дедуплицировать по содержимому: одинаковые строки существуют (PL 040 — три идентичные строки по артикулу, наименованию, габаритам и весу).
2. Границы строк находятся по горизонтальным линиям сетки; каждая строка получает порядковый номер в таблице. Полосы с перекрытием не должны давать дубли: строка принадлежит той полосе, в которой она целиком помещается.
3. В левую и правую половину каждой полосы добавляется колонка-якорь «Артикул» (склейка Pillow слева от правой половины), а в запрос — номера строк полосы. Модель возвращает значения по номерам строк.
4. Правая половина PL содержит колонку «Материал» (русское наименование) целиком; разрезать её между фрагментами нельзя.

### 5.5. Распознавание

**Рекомендуемый способ — модель Claude с компьютерным зрением и строгой JSON-схемой ответа.**
OCR (например, tesseract) хуже справляется с таблицами, печатью поверх текста и смешением кириллицы и латиницы. Если используется OCR, все проверки раздела 5.8 и второй проход раздела 5.6 становятся ещё важнее.

Правила запроса к модели (вписать в промпт):

1. Переписывать каждое значение **посимвольно как напечатано**, ничего не исправлять. Опечатки сохранять.
2. Числа возвращать **строкой как напечатано** (`"1 680,00 €"`), а разбирать их в коде (раздел 5.7). Так легче искать ошибки.
3. Если символ или значение не читается (например, под печатью) — **не угадывать**, а перечислить поле в `unreadable`.
4. Возвращать все строки таблицы и итоговую строку отдельно.
5. Коды ТН ВЭД — строкой.

Пример вызова на Python (Anthropic SDK). Параметры сверены с SDK `anthropic` 1.12.1; **реальный вызов API на пилоте не выполнялся** — проверить на эталоне (раздел 9).

                       "format": {"type": "json_schema", "schema": INVOICE_SCHEMA}},
        messages=[{"role": "user",
                   "content": [png_block(p) for p in fragment_paths]
                              + [{"type": "text", "text": instructions}]}],
    )
    if response.stop_reason == "refusal":
        raise RuntimeError(f"Модель отказалась: {response.stop_details}")
    if response.stop_reason == "max_tokens":
        raise RuntimeError("Ответ обрезан — увеличить max_tokens или уменьшить фрагмент")

### 5.6. Второй независимый проход (обязательно)

1. Распознать каждый документ **дважды** независимо: другая нарезка фрагментов и/или другая формулировка промпта.
2. Сравнить два результата **поле за полем**.
3. По каждому расхождению сделать третий запрос: дать сильно увеличенный фрагмент **одной ячейки** и спросить, что именно там напечатано (в пилоте именно так проверено Ш/Щ). Модель координат не возвращает, поэтому ячейку вырезает сама программа: строка — по порядковому номеру и линиям сетки (5.4), колонка — по положению строки заголовков. Строки двух проходов сопоставляются по порядковому номеру; если число строк разное — документ целиком отправляется на человеческую проверку (проект, не проверено в пилоте).
4. Если и после этого есть сомнение или поле есть в `unreadable` — пометить поле «требует проверки человеком» и показать в отчёте. Не угадывать.

### 5.7. Нормализация

Разбор чисел (проверено на всех значениях пилота):

```python
import re
from decimal import Decimal

def parse_number(raw: str) -> Decimal:
    """'€ 1 680,00' / '1 680,00 €' / '4500,000' / '13 567,15 €' -> Decimal"""
    s = raw.replace("€", "").replace("EUR", "")
    s = re.sub(r"[\s  ]", "", s)   # пробелы, NBSP, узкий NBSP
    s = s.replace(",", ".")
    if not re.fullmatch(r"-?\d+(\.\d+)?", s):
        raise ValueError(f"Не число: {raw!r}")
    return Decimal(s)
```

Прочие правила:

- `hs_code`: только цифры, ровно 10, хранить текстом.
- `qty`: целое.
- **Пробелы.** Во всех текстовых полях (`article`, `description_es`, `name_ru`, `dims_cm`) любую последовательность пробельных символов, включая перенос строки внутри ячейки (наименование в счёте может занимать две строки), заменять одним пробелом и обрезать края. **Больше ничего не менять.**
- **Латиница и кириллица.** Буквы A, B, C, E, H, K, M, O, P, T, X, Y (и строчные a, c, e, o, p, x, y) на скане выглядят одинаково в обоих алфавитах. В эталоне русские слова написаны кириллицей, а токены из цифр и букв (`21C`, `100A`, `4000V`, `SW4`, `PT100`, `CPCI`) и размеры (`200x260x150`) — латиницей. **Это решение составителя эталона: из скана оно не следует.** Поэтому (а) при сравнении с эталоном и при сравнении счёта с PL буквы приводятся к одному алфавиту функцией `fold`; (б) токены со смешением алфавитов попадают в отчёт как предупреждение (`mixed_script_tokens`).

```python
import re

_CYR2LAT = str.maketrans("АВЕКМНОРСТХУавекмнорстху", "ABEKMHOPCTXYabekmhopctxy")

def fold(s: str) -> str:
    """Привести визуально неразличимые кириллические буквы к латинским (только для сравнения)."""
    return s.translate(_CYR2LAT)

def mixed_script_tokens(s: str) -> list[str]:
    """Слова, в которых вперемешку кириллица и латиница."""
    return [t for t in re.findall(r"\S+", s)
            if re.search(r"[А-Яа-яЁё]", t) and re.search(r"[A-Za-z]", t)]
```
- `UN` → «шт» только при выводе в основную таблицу; в исходных данных оставить `UN`.

### 5.9. Распределение веса брутто

Если в месте одна позиция, её брутто = брутто места.

Если позиций несколько:

1. Доля позиции = брутто места × нетто позиции / нетто места, округлённая до 0,01 кг (математическое округление, ROUND_HALF_UP).
2. Остаток округления (брутто места − сумма долей) относится на позицию с **наибольшим нетто** в месте; при равенстве — на первую из них.
3. Сумма по месту обязана **точно** совпасть с брутто места из PL.
4. Такие значения помечаются как расчётные (в пилоте — жёлтая заливка).

```python
from decimal import Decimal, ROUND_HALF_UP

def allocate_gross(nets: list[Decimal], seat_gross: Decimal) -> list[Decimal]:
    total = sum(nets)
    shares = [(seat_gross * n / total).quantize(Decimal("0.01"), ROUND_HALF_UP) for n in nets]
    i_max = max(range(len(nets)), key=lambda i: (nets[i], -i))   # первая из наибольших
    shares[i_max] = seat_gross - (sum(shares) - shares[i_max])
    return shares

# Пилот, PL 041: нетто [12.60, 2.00, 0.20, 0.25, 1.20, 27.00], брутто места 75.00
#   -> [21.85, 3.47, 0.35, 0.43, 2.08, 46.82]
# Пилот, PL 042: нетто [0.50, 5.00, 2.00], брутто 10.00 -> [0.67, 6.66, 2.67]
```

Воспроизводить текст этих строк «один в один» не требуется; если нужна классификация — отдельный модуль с проверкой по тексту тарифа.

### 6.5. Пересчёт и контроль

openpyxl записывает формулы без вычисленных значений. Перед выдачей файла его нужно пересчитать (LibreOffice в headless-режиме) и убедиться, что ошибок `#NAME?`, `#VALUE!`, `#REF!` нет.
**В пилоте пересчёт зависал**, пока не был установлен пакет `libreoffice-calc`: без него LibreOffice не открывает xlsx («source file could not be loaded»).
После пересчёта: прочитать файл с `data_only=True` и сравнить значения с независимым расчётом в Python (в пилоте — все 40 строк, 0 расхождений).

## 9. Приёмочный тест

**Входной файл:** `8c38d916-supporting_4.pdf`, 14 страниц, SHA-256 `51b4f8775a22fcd2b35543a9808c51d3c20a698f21ae6cca29a7c3f4d9dedec6`. **В репозитории файла нет** (это документ заказчика с реквизитами сторон): исполнитель получает его отдельно и перед тестом сверяет контрольную сумму.
**Эталон:** `docs/golden/UZ95-039-045-2026_expected.json` — все 40 строк, напечатанные итоги, расчётный брутто и ожидаемые замечания (у каждого поле `required`).

**Правила сравнения с эталоном:**

- Текстовые поля (`article`, `name_ru`, `description_es`, `hs_code`, `um`, `packaging`, `dims_cm`) — посимвольно, после нормализации пробелов (5.7) и приведения похожих букв функцией `fold`. Это нужно потому, что выбор латиницы/кириллицы для `21C`, `100A`, `SW4`, `PT100`, `CPCI` и `x` в размерах сделан составителем эталона, а на скане буквы неразличимы.
- Числовые поля (`unit_price_eur`, `value_eur`, `unit_net_kg`, `net_kg`, `seat_gross_kg_printed`, `gross_kg_allocated`, все `printed_totals` и `expected_totals`) — как числа: `Decimal(факт) == Decimal(эталон)`. В эталоне они записаны без хвостовых нулей и без экспоненты (`"4500"`, `"1.8"`), а `parse_number` из 5.7 даёт `Decimal("4500.000")`, поэтому строковое сравнение недопустимо.
- Целые поля (`bulto`, `seat`, `qty`) — как `int`.

Программа принимается, если:

1. Распознаны все 7 пар документов, 40 строк, порядок строк — как в эталоне.
2. Все поля всех 40 строк совпадают с эталоном по правилам выше (включая «КЛЕШЕ» и «ЭЛЕКТРОНУМАТИЧЕСКИЙ»).
3. Итоги: 129 шт; 36 280,25 EUR по строкам; 36 131,69 EUR по TOTAL FACTURA; нетто 16 194,95 кг; брутто 17 665,00 кг.
4. Распределённый брутто каждой строки совпадает с `gross_kg_allocated`.
5. Найдены **обязательные** замечания (`required: true` в эталоне): `TOTAL_MISMATCH` (счёт UZ95-043-2026: 13 567,15 ≠ 13 715,71, разница 148,56), `SAME_NAME_DIFFERENT_HS` (Z5050055A против Z5050054A / 57A / 58A), `PALLET_NUMBER_REUSED` (паллета 2 в счетах 041 и 042). **Желательные** (`required: false`): `PALLET_NUMBER_GAP` (нет паллет 8 и 9) и два `SOURCE_TYPO` (Z10014704, Z594470).

## 10. Ограничения

- Координаты фрагментов в пилоте подобраны под этот макет счёта Talgo. Для другого макета нужна автоматическая детекция таблицы или новая настройка.
- Распознавание моделью не даёт 100 % гарантии. Поэтому обязательны второй проход (5.6), арифметические проверки (5.8) и пометка неуверенных полей.
- Коды ТН ВЭД проверяются только на формат и внутреннюю согласованность. Правильность классификации программа не определяет; замечания пилота по классификации — сведения ИИ-ассистента без сверки с тарифом.
- **Разделы 5.4–5.6 — проект.** Автоматическая нарезка, сборка строк, вызов API и второй проход в пилоте не реализовывались и не запускались. Пример вызова в 5.5 проверен только по сигнатуре SDK (`anthropic` 1.12.1) и на компиляцию, без обращения к API.
- Исходный скан имеет разрешение 200 ppi; рендер 300 dpi читаемость повышает только за счёт удобного масштаба.
- В пилотном Excel проверки С3–С5 тавтологичны (раздел 2, п. 4).
