## 1. Схема: что раздувает грамматику и какие варианты проверить

### Что известно точно (документация Claude API, раздел Structured Outputs)

- Явные лимиты: ≤ 20 строгих инструментов, ≤ 24 необязательных параметра, ≤ 16 параметров с объединением
  типов (anyOf или `["string","null"]`). У нас 0 необязательных и 0 объединений, то есть явные лимиты соблюдены.
- Кроме них есть **внутренний лимит на размер скомпилированной грамматики**, без чисел. Документация советует:
  меньше необязательных полей, проще вложенность, разделить запрос на несколько.
- **Описания, скорее всего, ни при чём.** По документации смена только `name` или `description` не сбрасывает
  кеш скомпилированной грамматики. Значит, описания в грамматику, вероятно, не входят.

### Что, по-моему, раздувает грамматику (предположения, по убыванию вероятности)

1. **Общее число полей после раскрытия `$ref`.** Вы насчитали 60, но с раскрытием ссылок полей 80:
   три `Party` в шапке, `WireShipment` дважды, два почти одинаковых объекта позиции (12 и 16 полей).
   Каждое поле — это имя-литерал и правило значения в грамматике.
2. **Объекты позиций внутри массивов.** Шаблон позиции с 16 полями повторяется в цикле, а таких массивов два
   (позиции эталона и новые). Варианты d и e убирают имена полей позиций совсем.
3. **Глубина вложенности 4** (result → reference → header → party). Документация прямо называет вложенность
   фактором роста.
4. Enum (2 штуки по 3 значения) и `integer` — вряд ли заметны.

Как именно API считает размер, я не знаю. Поэтому ниже варианты, которые уменьшают схему по разным осям,
и режим `--probe`, который проверяет схему full по частям и показывает, какая часть не проходит.

### Варианты (ветка `claude/practical-darwin-sqjl21`, коммит 4d6b177)

Переключение: `LLM_SCHEMA_VARIANT=<вариант>` в `.env` или в админ-панели («Вариант схемы ответа ИИ»),
без перезапуска. По умолчанию `full`: запрос к API байт в байт прежний.

| Вариант | Что меняется | Полей (с `$ref`) | Байт | Вызовов |
|---|---|---|---|---|
| full | текущая схема | 80 | 10 062 | 1 |
| a | без description и title | 80 | 4 299 | 1 |
| b | без `item_no` и `unit_price` у позиций, короткая отгрузка эталона | 71 | 9 572 | 1 |
| c | два вызова: (1) эталон, (2) новые поставка и позиции | 54 + 31 | 6 697 + 5 532 | 2 |
| d | позиции таблицей: каждая строка — массив строк в фиксированном порядке колонок | 52 | 5 414 | 1 |
| e | c и d вместе | 42 + 15 | 4 897 + 2 897 | 2 |

Мой прогноз шансов на приём, от большего к меньшему: **e, d, c, b, a**.
- Вариант a я жду отклонённым: описания, вероятно, не входят в грамматику. Но проверка бесплатная.
- Чтобы c или e работали, API должен принять **обе** части.

**Как проверить** (отклонённый запрос не оплачивается, принятый стоит доли цента):

```bash
python scripts/check_llm_schema.py --stats            # размеры всех вариантов, без запросов к API
python scripts/check_llm_schema.py --variant all      # все варианты по очереди
python scripts/check_llm_schema.py --probe            # full по частям + контрольная схема из 1 поля
python scripts/check_llm_schema.py --variant all --model claude-sonnet-5-5   # если интересно, зависит ли от модели
```

Как читать `--probe`:
- **Контрольная схема из 1 поля отклонена** — дело не в размере (ключ, модель или параметры). Пришлите
  точный текст ошибки.
- **Отдельные части проходят, целая схема нет** — лимит на суммарный размер. Выбирайте самый крупный
  принятый вариант.

**Что учесть при выборе:**
- **c и e:** два вызова. Документы эталона читаются только в первом, второй получает извлечённый эталон
  в JSON. Стоимость примерно та же, время то же или чуть больше. Лимит обработок в сутки считает это одной
  обработкой.
- **d и e:** если модель пропустит колонку в строке, обработка завершится понятной ошибкой «в строке N
  … значений вместо 16». Сдвиг колонок перепутал бы вес со стоимостью, поэтому такой ответ не принимается.
  Ещё d и e, вероятно, дешевле по выходным токенам: имена полей не повторяются в каждой позиции.
  Я это не измерял.
- **b:** цена за единицу в результате будет пустой. Валидатор и экспорт её не требуют.

Код: `app/services/schema_variants.py`, тесты: `tests/test_schema_variants.py`. Все варианты дают
одинаковый результат на демо-данных, и каждый укладывается в явные лимиты.

## 2. ASYCUDA: если импорт снова не пройдёт

### а) Что вероятнее всего сломается следующим

1. **Курс и стоимость в лари (графа 23).** Курс по умолчанию берётся из старой декларации. Пересчитывает ли
   ASYCUDA курс сама при импорте или проверке, **я не знаю**.
2. **Предыдущий документ при процедуре 7474.** Блок `Prev_decl` и «Предыдущий документ» в позиции копируются
   из основы как есть, включая списанные места и вес. При новых количествах ASYCUDA, вероятно, сообщит
   о расхождении списания.
3. **Код товара.** Если на сайте код из 10 цифр, `Precision_1` получится из 2 цифр вместо 3 — тарифная
   строка может не найтись. Если код из 8 цифр и не совпадает с образцом, `Precision_1` остаётся пустым.
4. **Дополнительные единицы измерения.** Если код позиции отличается от образца, они очищаются. Для товаров,
   где они обязательны, ASYCUDA потребует количество.
5. **Несколько позиций.**
   - Документы графы 44 копируются в каждую позицию.
   - Число листов считается по формуле 1 + ⌈(N−1)/3⌉ (бланк ЕАД: одна позиция на первом листе, по три
     на добавочных).
   - Строка `Value_item` (`0.00+0.00+0+0.00-0`) копируется из образца.

   Проверено только на файле с одной позицией.
6. **Даты в графе 44** пишутся как M/D/YY (так в выгрузке). Дата инвойса в нераспознанном формате
   остаётся пустой.
7. **Описание на английском**, если инвойс английский и такого товара нет в эталоне. Импорт пройдёт, но
   таможне, вероятно, нужен грузинский.

### б) Самые неуверенные места кода (`app/services/asycuda.py`)

| Функция | Что под вопросом |
|---|---|
| `_fill_valuation` | распределение затрат по доле стоимости (α), статистическая стоимость = CIF, курс из основы |
| `_fill_hs` | деление кода: 8 цифр + остаток; 8-значный код без уточнения |
| `_fill_totals` | формула числа листов; вес брутто итого — сумма позиций |
| `_replace_documents` | замена только при точном совпадении номера; копия документов в каждую позицию; формат даты |
| `_fill_supplementary_units` | очистка при смене кода |
| `render` | `Prev_decl` не меняется; образец позиции — по `reference_item_no` |
| `_country` / `_country_index` | числовой ISO-код страны (подтверждён только на BR = 76 и GE = 268) |
| `choose_base` | чистый бланк + эталон из ASYCUDA → основа — эталон |

## 4. Длина кода ТН ВЭД

- **Нужно ли 11 знаков?** В присланном файле ASYCUDA код записан как 8 цифр (`Commodity_code`) + 3 цифры
  (`Precision_1`) = 11. Официальную длину грузинского национального кода **я точно не знаю**.
- **Что изменится при `HS_CODE_LENGTH=11`** (или в админ-панели «Цифр в коде ТН ВЭД» = 11, сразу, без
  перезапуска):
  - коды из 11 цифр перестанут помечаться ошибкой «должен состоять из 10 цифр»;
  - коды из 10 цифр начнут помечаться;
  - утверждение это не блокирует: замечания показываются, но утвердить можно.
- **Старые задачи:** уже сохранённые замечания не пересчитываются. При повторном утверждении проверка идёт
  по новой длине.
- **Экспорт в ASYCUDA:** 11 цифр делятся правильно (8 + 3), это тоже аргумент за 11.
- **Промпт** длину не упоминает, ему всё равно.
- **Рекомендую поставить 11**, предварительно проверив по 2–3 другим декларациям этого брокера, что везде
  8 + 3.

9. **Итоги:** только если напечатаны. Допуски сверки: деньги 0,01, вес 0,5 %. Нетто больше брутто —

10. **Коды из ASYCUDA:** `Commodity_code` + `Precision_1` склеиваются в один код.

## 6. Деньги

**Что увидит пользователь, если баланс кончится.**
- API отвечает ошибкой 400. Насколько я знаю, текст: «Your credit balance is too low to access the
  Anthropic API…». На настоящем API в этом проекте это не проверялось.
- **До коммита 4d6b177** на странице задачи было «Запрос отклонён API: Your credit balance is too low…»:
  понятно, но по-английски внутри русской фразы.
- **С 4d6b177** — «На счёте Anthropic закончились деньги. Пополните баланс в консоли Anthropic (Billing)
  и повторите обработку», на трёх языках. Сообщение срабатывает, если в ответе API есть слова
  «credit balance»; иначе остаётся прежний вариант с текстом API.
- Задача уходит в «ошибку», после пополнения — «Повторить обработку».
- Работает ли бесплатная кнопка «Проверить ключ» при нулевом балансе, **я не знаю**.

**Лимиты в админ-панели — да, меняются сразу.**
- Где: Настройки → «Обработок в сутки на пользователя» и «Обработок в сутки на весь сайт» (0 — без лимита).
- Как считается: одна загрузка или повтор = одна обработка, даже если вариант схемы делает два вызова.
- Окно: последние 24 часа.

**Совет на $5** (одна обработка по замерам ≈ $0,13–0,73; $5 хватит на ~6 больших сканов или ~35 маленьких
файлов):
- **«На весь сайт» = 5, «на пользователя» = 3** — пока баланс $5 и автопополнение выключено.
- В консоли Anthropic задайте месячный лимит расходов и уведомление о низком балансе, если такие настройки
  есть в вашем разделе Limits / Billing.
- В админ-панели «Обзор» показывает примерный расход за 30 дней по нашей таблице цен.

**Как сделать дешевле** (решение за пользователем, качество нужно проверить на реальных документах):
- `LLM_EFFORT=medium` вместо `high`: меньше токенов рассуждения.
- Варианты схемы d / e: короче ответ.
- Модель Sonnet 5.5: вдвое дешевле Opus 5.5.
